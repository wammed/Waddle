### コマンド実行セキュリティ

主要なコマンド実行境界は以下の通りです：

```text
AI / UI
   ↓
Rust CommandPolicy
   ├── SAFE   → 実行 (execute)
   ├── REVIEW → 明示的な確認が必要 (explicit confirmation required)
   └── BLOCK  → 実行拒否 (execution denied)
   ↓
PTY master write
```

重要なセキュリティ特性は、**フロントエンドの確認が唯一の強制メカニズムではない**ということです。コマンドはPTY書き込みの直前にRustバックエンドによって再評価されます。

現在のコマンドポリシーコーパスには、破壊的コマンド、特権昇格、シェル間接実行、インタプリタ評価、クレデンシャルアクセス、環境変数漏洩、シェル難読化、複数行コマンド実行など、**13のカテゴリにわたる113のテストベクター**が含まれています。

### SSRF / Ollama セキュリティ

Ollamaのエンドポイント処理は、DNS解決を実行し、接続前に解決されたアドレスを検証します。禁止されているメタデータ/リンクローカルアドレスは拒否され、リダイレクトは無効化され、接続は検証済みの解決済みアドレスにピン留めされます。

これにより、現在の実装と回帰テストでカバーされている主要なSSRFおよびDNSリバインディングシナリオに対する保護が提供されます。

### ファイルシステムセキュリティ

ファイルシステム操作は、以下のセキュリティ境界を適用します：

* パストラバーサル
* `/proc`
* `/sys`
* `/dev`
* SSH秘密鍵
* GPG秘密鍵 / キーリング
* クラウドクレデンシャル
* `.env`
* シンボリックリンクエスケープ
* 所有権

エディタの保存では、置換前に同期を伴う一時ファイルとアトミックリネームのアプローチを使用します。

残る堅牢化の課題としては、検証/正規化とそれに続くファイルシステム変更の間の**TOCTOU（Time-of-check to time-of-use）クラスのファイルシステム競合状態**があります。より高い保証を求める実装では、`openat` / `O_NOFOLLOW` などのファイルディスクリプタ相対操作を通じて、このクラスのリスクをさらに軽減することができます。

### 運用上のリリース要件

CIワークフローはリリースゲートを定義していますが、リポジトリ構成でもこれを運用上強制する必要があります。

本番環境のブランチ（production branches）では、対応するGitHubのブランチ保護 / リポジトリルールセットにより、以下の4つのリリースCIジョブの正常完了を必須とする必要があります：

* **Security & Dependency Audit**
* **Rust Backend Tests & Clippy**
* **Frontend Unit & Coverage Gate (80%+)**
* **Build Verification (Vite & Tauri)**

YAMLワークフロー自体はブランチ保護を強制するものではないため、その要件はリポジトリ設定で構成する必要があります。
